## 1. Introduction

XO License is an independent open-source licensing initiative created by **OTTAHEN (ℒ)**.

The objective of XO is to give developers, organizations, researchers, businesses and independent creators the freedom to **use, modify, distribute and commercialize** software while preserving recognition of the original creators.

XO combines permissive software licensing principles with a structured **attribution and software-origin ecosystem**.

Traditional licenses focus mainly on permissions and copyright notices. XO goes further: it establishes a broader **creator-recognition framework** in which the history of a project can travel with the project itself.

### 1.1 Why XO Exists

Modern software is built in layers. A single product may contain code from dozens of projects, forked many times, renamed, relocated across platforms, acquired by companies and repackaged. In that process, the people who created the original work are often forgotten, and the path from original to derivative is lost.

XO exists to solve this problem without taking away any freedom:

- Developers should be **free** to build, fork and sell.
- Creators should be **recognized** wherever their work goes.
- Users should be able to **see** where software came from.
- Attribution should be **easy** to keep and hard to lose.

### 1.2 Core Philosophy

| Principle | Meaning |
|---|---|
| **Freedom of Development** | Build on anything, commercially or personally |
| **Creator Recognition** | Credit goes with the work |
| **Attribution Continuity** | Credit survives forks, renames and transfers |
| **Software Transparency** | Origins can be inspected and verified |
| **Intellectual Property Protection** | Patents, trademarks and authorship are addressed clearly |
| **Commercial Freedom** | No royalties, no revenue share, no field-of-use limits |
| **Decentralized Verification** | No central server is required to prove origin |

### 1.3 Fundamental Principle

> **Anyone can build upon your work. Anyone can improve it. Anyone can commercialize it. But nobody should be able to erase where it came from.**

### 1.4 Design Goals

1. **Simple to adopt:** one license file and one origin record.
2. **Simple to follow:** attribution requirements that fit normal project practice.
3. **Hard to lose credit:** origin information is structured, portable and signable.
3. **Commercially friendly:** no forced source disclosure and no royalties.
4. **Tool-friendly:** every rule can be checked automatically.
5. **Community-governed:** open revision process and independent review.

### 1.5 What XO Is Not

- XO is **not** copyleft. You are never forced to publish your own source code.
- XO is **not** a payment scheme. No royalties or revenue sharing.
- XO is **not** a registration requirement. The registry is optional.
- XO is **not** a restriction on independent work. Similar ideas do not create a derivative.

## 4. Attribution & Creator Recognition System

Attribution is the **defining feature** of XO.

### 4.1 Mandatory Original Author Credit
Redistributors must provide appropriate credit to the original author or copyright holder.

### 4.2 Original Project Name Preservation
The original project name must remain identifiable in accompanying attribution information, even when derivative projects use different names.

### 4.3 Copyright Notice Preservation
Original copyright notices must be retained in redistributed copies.

### 4.4 Contributor Recognition
Contributors can receive individual recognition for their contributions.

### 4.5 Upstream Attribution Preservation
Attribution to upstream creators must not be deliberately removed from derivative distributions.

### 4.6 Attribution Continuity
Credit should survive repository transfers, project renaming, organizational changes and redistribution.

### 4.7 Modification Identification
Distributors must clearly identify when a version has been modified.

### 4.8 No False Authorship
Nobody may falsely claim that another person's original work is entirely their own.

### 4.9 No False Endorsement
Derivative projects cannot falsely imply official endorsement or sponsorship by the original creator.

### 4.10 Flexible Credit Placement
Attribution can be provided through:

- README files
- LICENSE files
- NOTICE files
- Documentation
- Accompanying attribution documents
- Appropriate project information pages

XO does **not** require mandatory attribution banners inside an application's user interface.

### 4.11 Multi-Author Attribution
Projects with multiple original creators must be able to preserve their respective copyright and contributor information.

### 4.12 Historical Attribution
Previously supplied attribution records should remain available when project ownership or maintainership changes.

### 4.13 Binary Distribution Attribution
Distributors of compiled binaries must provide accessible attribution notices accompanying the binary or its distribution materials.

### 4.14 SaaS Distribution Clarification
XO distinguishes private internal software use from distribution of software copies. Merely operating a private service does not automatically trigger source publication or attribution obligations.

### 4.15 Attribution Placement Matrix

| Distribution type | Where attribution may appear |
|---|---|
| Source repository | `LICENSE`, `README.md`, `NOTICE`, `XO-ORIGIN.json` |
| Package (npm, PyPI, Cargo, Maven) | Package metadata, bundled `NOTICE`, bundled `LICENSE` |
| Compiled binary or installer | Accompanying notice file, "About" screen, or distribution documentation |
| Mobile app | Store listing, settings or about page, or accompanying documentation |
| Hosted service (no copies distributed) | No obligation unless copies are distributed |
| Container image | Bundled `NOTICE` and `LICENSE` files in the image |

### 4.16 Recommended Attribution Notice

```
This product includes software originally created by <Original Creator>
(<Original Project Name>), licensed under the XO License, Version 1.0.
Original project: <repository URL>
This version has been modified by <Modifier> on <date>.
```

## 5. XO Origin Technology

**Signature Innovation: Software Provenance and Attribution Continuity.**

### 5.1 XO Origin Chain
Maintains a structured record of the relationships between original projects and their derivatives.

```
Original Project
      |
      v
Original Creator
      |
      v
Developer A  -  Modification
      |
      v
Developer B  -  Fork
      |
      v
Company C    -  Commercial Version
      |
      v
Developer D  -  Further Derivative
```

The system preserves origin information while allowing independent development.

### 5.2 XO Origin ID
A unique identifier for registered projects, helping distinguish original projects from similarly named projects.

Proposed format:

```
XO-<CATEGORY>-<NUMBER>
Example: XO-EXAMPLE-001
```

### 5.3 XO Attribution Map
A visual representation of project origins and contribution relationships. It displays:

- Original creator
- Original project
- Contributors
- Derivative projects
- Fork relationships
- Modification records
- Known upstream dependencies

### 5.4 XO Origin Verification
An optional verification mechanism using cryptographic hashes and digital signatures.

### 5.5 XO Origin Record
A standardized metadata file: **`XO-ORIGIN.json`**. It can contain:

- Project identifier
- Original project name
- Creator information
- Repository reference
- License version
- Upstream project identifiers
- Contributor information
- Modification summaries
- Record version
- Optional cryptographic signatures

### 5.6 XO Credit Continuity
Preserves original creator attribution when software is forked, renamed, transferred or redistributed.

### 5.7 XO Project Lineage
Allows users to inspect known project development relationships without assuming every fork is an official continuation.

### 5.8 XO Change Identity
Separates original project identity from derivative modifications.

### 5.9 XO Contributor Graph
Displays contributors and their documented relationships to different project versions.

### 5.10 XO Origin Timestamp
Records when an origin record or signature was created. Timestamps are metadata, not automatic proof of authorship.

### 5.11 XO Origin Portability
Origin information should remain portable across GitHub, GitLab, Codeberg and self-hosted Git repositories.

### 5.12 XO Historical Record
Maintains an optional history of significant origin-record changes.

### 5.13 XO Provenance Export
Allows origin and attribution records to be exported into JSON, YAML or human-readable documentation.

### 5.14 XO Provenance Import
Allows developers to import existing attribution information when migrating projects.

### 5.15 How the Origin Chain Works in Practice

1. **Create.** The original creator adds `LICENSE` and `XO-ORIGIN.json`.
2. **Fork.** A developer forks the project. Their copy keeps the original record.
3. **Record.** The developer adds an entry to `modifications` and `upstream`.
4. **Distribute.** The derivative is released with attribution and the updated record.
5. **Repeat.** Each later derivative adds a new entry. Earlier entries are never erased.
6. **Verify.** Anyone can inspect the chain, and signed records reveal tampering.

### 5.16 Origin Chain Rules

| Rule | Description |
|---|---|
| Append-only history | Earlier upstream and modification entries must not be removed |
| No forged lineage | Entries must reflect actual derivation |
| Independent identity | Derivatives may use their own name, branding and Origin ID |
| Portable | Records must work on any hosting platform |
| Optional signing | Signatures strengthen records but are never required |

### 9.10 Long-Term Metadata Compatibility
Keeps origin records readable across future ecosystem versions.

### 9.11 Attribution Correction Process (Outline)

1. A person or project identifies inaccurate or missing attribution.
2. They open a correction request with evidence.
3. The maintainer reviews and responds within a reasonable period.
4. The corrected record is published, and the previous version is kept in the historical record.
5. Disputes may be escalated to community review.

## 11. XO Technical Standards

### 11.1 XO-ORIGIN.json

The proposed standard metadata format for origin and attribution information.

```json
{
  "format": "XO-ORIGIN",
  "version": "1.0",
  "license": "XO-1.0",
  "project": {
    "name": "Example Project",
    "origin_id": "XO-EXAMPLE-001",
    "repository": "https://example.com/original"
  },
  "creator": {
    "name": "Original Creator"
  },
  "upstream": [],
  "contributors": [],
  "modifications": [],
  "verification": {
    "method": "optional-digital-signature",
    "signature": null
  }
}
```

> This is an illustrative proposed schema. It is not an established standard.

### 11.2 Field Reference

| Field | Type | Required | Description |
|---|---|:---:|---|
| `format` | string | Yes | Always `"XO-ORIGIN"` |
| `version` | string | Yes | Record format version |
| `license` | string | Yes | License identifier, e.g. `XO-1.0` |
| `project.name` | string | Yes | Project name |
| `project.origin_id` | string | No | XO Origin ID if registered |
| `project.repository` | string | Yes | Canonical repository URL |
| `creator.name` | string | Yes | Original creator or copyright holder |
| `upstream` | array | No | Projects this one derives from |
| `contributors` | array | No | Documented contributors |
| `modifications` | array | No | Summaries of changes |
| `verification.method` | string | No | e.g. `optional-digital-signature` |
| `verification.signature` | string/null | No | Signature value |

### 11.3 Example: Derivative Project Record

```json
{
  "format": "XO-ORIGIN",
  "version": "1.0",
  "license": "XO-1.0",
  "project": {
    "name": "Example Project Plus",
    "origin_id": "XO-EXAMPLE-014",
    "repository": "https://example.com/plus"
  },
  "creator": {
    "name": "Derivative Maintainer"
  },
  "upstream": [
    {
      "name": "Example Project",
      "origin_id": "XO-EXAMPLE-001",
      "creator": "Original Creator",
      "repository": "https://example.com/original",
      "relationship": "fork"
    }
  ],
  "contributors": [
    { "name": "Contributor One", "contribution": "plugin system" }
  ],
  "modifications": [
    {
      "date": "2026-11-09",
      "by": "Derivative Maintainer",
      "summary": "Added plugin system and rewrote build scripts"
    }
  ],
  "verification": {
    "method": "optional-digital-signature",
    "signature": null
  }
}
```

### 11.4 Validation Rules

1. The file must be valid UTF-8 JSON.
2. `format`, `version`, `license`, `project` and `creator` must be present.
3. `license` must match the project's `LICENSE` file.
4. For derivatives, `upstream` must contain at least one entry.
5. Earlier `upstream` and `modifications` entries must not be removed.
6. Dates must follow ISO 8601.
7. Unknown fields must be ignored, not rejected.

### 11.5 File Naming Convention

Recommended files:

```
LICENSE
README.md
NOTICE
AUTHORS.md
CONTRIBUTORS.md
XO-ORIGIN.json
```

Not every file is mandatory for every project. The actual license and attribution requirements determine what must accompany a distribution.

### 11.6 Metadata Portability
XO records should use open, documented formats that can be processed by independent tools.

### 11.7 Cryptographic Integrity
Optional cryptographic verification should make unauthorized changes to signed records detectable.

### 11.8 Decentralized Operation
The system should continue functioning without a centralized XO server.

### 11.9 Versioning Policy

| Change | Version impact |
|---|---|
| Wording clarification with no change in meaning | Patch (1.0.1) |
| New optional feature or tool | Minor (1.1) |
| Change to permissions or obligations | Major (2.0) |

Released versions are never silently changed. Projects choose which version applies to their code.

## 13. How to Adopt XO

### 13.1 Quick Start

1. Add the XO License text to a file named `LICENSE` in your repository root.
2. Replace `[YEAR]` and `[COPYRIGHT HOLDER]`.
3. Add an `XO-ORIGIN.json` file (see Section 11).
4. Add a short notice to your `README.md`.
5. Optionally add the XO badge.
6. Commit and release.

### 13.2 README Notice

```markdown
## License

This project is licensed under the XO License, Version 1.0.
See [LICENSE](LICENSE) for details.

XO License created by OTTAHEN (ℒ), https://github.com/Ottahen
BUILD FREELY. CREDIT FOREVER.
```

### 13.3 Badge

```markdown
![License: XO-1.0](https://img.shields.io/badge/license-XO--1.0-blue)
```

### 13.4 Optional Source File Header

```text
Licensed under the XO License, Version 1.0.
See LICENSE and XO-ORIGIN.json for attribution and origin information.
```

### 13.5 Forking an XO Project

1. Fork or copy the project and keep `LICENSE`, `NOTICE` and `XO-ORIGIN.json`.
2. Add the original project to your `upstream` list.
3. Add a `modifications` entry describing your changes.
4. Mark modified files or document changes in your release notes.
5. Rename and rebrand freely, but keep upstream attribution.
6. Release with an updated attribution notice.

### 13.6 Moving a Repository

1. Copy all license and origin files to the new location.
2. Update `project.repository`.
3. Keep the full `upstream` and `modifications` history.
4. Optionally record the move in the historical record.
5. Validate with `xo check`.

## 15. Real-World Scenarios

### Scenario 1: Startup Uses an XO Library in a Paid App
A startup includes an XO-licensed library in its closed-source product and sells it.
**Allowed.** It keeps the notice and attribution in its documentation or about page. No royalties and no source publication are required.

### Scenario 2: Developer Forks and Renames
A developer forks an XO project, renames it and adds features.
**Allowed.** The developer keeps upstream attribution, adds an `upstream` entry and records modifications.

### Scenario 3: Company Removes the Original Author's Name
A company ships a derivative with all original credits stripped.
**Not allowed.** This violates attribution preservation and false authorship terms. The company has 30 days to cure after notice.

### Scenario 4: Private Internal Modification
A team modifies XO software for internal use and never distributes it.
**Allowed.** No publication or attribution obligation arises from private use.

### Scenario 5: Independent Reimplementation
A developer writes similar software from scratch without copying XO code.
**Allowed.** Independent work is not a derivative.

### Scenario 6: Repository Transfer
A maintainer moves a project from one host to another.
**Allowed and supported.** Attribution and origin records must move with it.

### Scenario 7: Open Source Distro Bundles Many Packages
A distribution bundles XO packages.
**Allowed.** The distribution provides notices accompanying the packages or its distribution materials.

## 16. Frequently Asked Questions

**Can I use XO software commercially?**
Yes. No royalties and no revenue share.

**Do I have to publish my modifications?**
No. Private modifications stay private.

**Do I have to open-source my whole product?**
No. XO is not copyleft. You may integrate XO software into proprietary applications.

**Do I need to show attribution inside my app's interface?**
No. Attribution can live in documentation, NOTICE files or similar accompanying materials.

**Can I rename my fork?**
Yes. You must keep upstream attribution and original project identification.

**What if I accidentally removed attribution?**
Your rights terminate, but they are reinstated if you fix the problem within 30 days.

**Is registration required?**
No. The registry is optional.

**Does the XO website need to stay online?**
No. Origin records are decentralized and verifiable offline.

**Does running XO software as a web service require attribution?**
Not merely by operating a private service. Distribution of copies is what triggers obligations.

**Can I combine XO code with GPL or MIT code?**
In general you may combine XO software with software under other licenses as long as each license's conditions are met. Check specific license compatibility for your case.

**Who owns my contributions?**
You do. XO identifies the origin of the license initiative and does not take ownership of others' work.

**Is XO approved by the OSI?**
Not yet. See Section 23.

## 18. Open Source Compatibility & Governance

XO should be designed for broad adoption. Its development should follow these principles:

1. Preserve the freedoms required by the Open Source Definition.
2. Do not prohibit commercial use.
3. Do not restrict fields of endeavour.
4. Do not discriminate against individuals or groups.
5. Do not require centralized project registration.
6. Avoid unnecessary technical restrictions.
7. Keep license terms understandable.
8. Document compatibility with other licenses.
9. Maintain a transparent revision process.
10. Allow community feedback and independent review.

Mandatory attribution must be carefully scoped to copyright and provenance notices, rather than creating restrictions on independent software or unrelated downstream projects.

### 18.1 Governance Model

| Element | Approach |
|---|---|
| Steward | OTTAHEN (ℒ) |
| Changes | Proposed publicly, discussed openly, released as new versions |
| Review | Independent legal and community review |
| Transparency | All drafts, issues and decisions public |
| Stability | Released versions are never altered |

### 18.2 Revision Process

1. Proposal opened as a public issue.
2. Community discussion period.
3. Draft published for review.
4. Legal and technical review.
5. Release as a new version with a changelog.

## 22. Glossary

| Term | Definition |
|---|---|
| **Attribution** | Credit given to the original creator or copyright holder |
| **Binary distribution** | Distribution of compiled software rather than source code |
| **Copyleft** | A licensing model requiring derivatives to be shared under the same terms; XO-1.0 is not copyleft |
| **Contributor** | Anyone who contributes code, documentation or other material |
| **Derivative Work** | A work based on or derived from the Software, including forks, ports and modified versions |
| **Fork** | A copy of a project that develops independently |
| **Lineage** | The documented chain of origin from original to derivative |
| **Origin ID** | Identifier that distinguishes a registered project |
| **Origin Record** | The `XO-ORIGIN.json` file describing origin, creators and modifications |
| **Origin Chain** | The linked series of origin records across derivatives |
| **Provenance** | The documented history of where software came from |
| **SaaS** | Software offered as a hosted service |
| **SPDX** | A standard for identifying software licenses |
| **Upstream** | A project that another project is derived from |
